## 2. 技術方針

初期はJavaScript ES Modules、純粋core、標準テストランナーを基本とする。実装開始時に利用可能なNode LTSを確認し、使用majorとlockfileを記録する。新たな本番ランタイム依存は必要最小限とする。

開発用分割ソースからTampermonkey向け単一userscriptを生成する。ビルド成果物にengine/ruleset/schema版を埋め込み、生成物を手編集しない。ビルド再現性、構文、同一入力の判断をCI対象にする。依存/ビルドツールの確定はM1の環境確認で記録し、設計文書の時点で未確認版を指定しない。

## 3. 導入・設定移行

- 新しい設定キーとschemaVersionを使用する。旧版の補正重み、待機上限、購入進行保証を持ち込まない。
- 初回は観測モード。対応版と診断が正常であることを表示し、通常自動化を有効化できる。
- 操作機能ごとにcapabilityと許可設定を表示。不可逆操作は個別許可。
- v8.0以前を無効化して再読み込みする手順を必須の導入説明へ含める。
- 停止時はGameセーブを変更しない。ロールバックは旧版へ戻す前に新版を停止し、二重起動を避ける。
- 設定移行前の旧設定は保持する。セーブエクスポートはユーザーが管理し、診断公開に含めない。

## 4. 明示的な設計上の選択

| 論点 | 初期決定 | 再検討条件 |
| --- | --- | --- |
| 最適化目的 | 成長、複数期間資産と目標ETA | 比較試験で特定段階が退行 |
| 長期投資 | 共通期間を最短回収経路から延長 | 高価値解禁を見落とすfixture |
| 固定序盤手順 | 強制せず既存取得順を基準試験化 | 正確な経済モデルでも要件と不整合なら条件を報告 |
| 未知Upgrade | 保持、追加証拠、無根拠自動購入なし | 対応Rulesetの追加 |
| 予約切替 | 成功/明示無効化/成立不能のみ解除 | 自動再目標化を保証付きで設計できた時 |
| 探索上限 | 固定node/event上限、決定的縮退 | 実ブラウザの応答性能測定 |
| 乱数 | 未来予知なし、固定模擬シナリオ | 分布モデルの誤差が検出された時 |
| 仮想測定 | 対応版と監査済みフィールドのみ | Mod/更新による副作用差分 |
| 転生 | パッケージ比較の助言 | 明示許可と終了処理試験の完了 |

## 5. 実装前・実装中に解消する事項

これはユーザーへの追加承認要求ではなく、各段階の担当実装で確認する技術課題である。

1. 実画面から報告当時の完全状態は未取得。合成fixtureを実画面再現と混同しない。
2. 公式ソースの取得ハッシュは記録済みだが、ブラウザのGame.versionとModの対応確認はM3で行う。
3. Game仮想測定の全副作用、価格/購入API、bulk/売買モード、pendingの実際の発生条件はM3で監査する。
4. 短中長期間・リスク係数・探索幅は設計初期値であり攻略上の最適値ではない。M2以降の感度試験で調整する。
5. 未知効果や長期予約により停止して見えるケースは残りうる。理由・不足情報を表示し、無根拠Fallbackで隠さない。
6. Season、Dragon操作、特殊Upgrade buyFunction等の詳細対応は該当段階で追加一次資料を確認する。
7. ランダムなGC/農園/市場の模擬分布は実ゲーム全体の完全な複製ではない。誤差と未対応要素を結果へ併記する。
8. 1024 node/4096 eventなどの上限は実ブラウザで未測定。重い場合はイベント圧縮/分割計算を検討し、判断決定性を維持する。
9. JSON validatorと例示fixtureはM1で実装する。本変更はMarkdownのみで、実行可能なschema/テストはまだ存在しない。

## 6. リリース報告の要件

何を実装したか、どのfixtureが通ったか、実画面のどの段階まで確認したか、攻略ベンチマークの条件と結果、未対応能力を記載する。「修正済み」は対象ケースの実画面確認範囲に限定する。未実施をpassへ変換しない。
