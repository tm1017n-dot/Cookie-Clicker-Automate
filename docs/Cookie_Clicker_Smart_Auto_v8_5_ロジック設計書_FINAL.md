# Cookie Clicker Smart Auto v8.5 ロジック設計書

対象はCookie Clicker Web版をTampermonkeyで自動操作するユーザースクリプトです。v8.5は通常購入の失敗後に使われる最終復帰処理が、ROIを無視して最安候補を買っていた問題を修正します。

原因はUpgrade目標を作る直前に、`upgradePriority`または`critical`が付いた候補だけへ絞り込んでいたことです。購入後の実測増産量と回収時間が優秀な通常Upgradeでも、この分類フラグがなければ投資目標になれませんでした。その結果、後段のBeam Searchや価格ベースFallbackまで流れ、実質的に施設との価格比較で購入時期が決まっていました。

## 1 変更概要

v8.4からの修正は次のとおりです。

- 最終復帰候補の価格順ソートを廃止
- 施設は価格を実効増産量で割った回収時間を計算
- Upgradeも仮想購入差分と効果推定から回収時間を計算
- 効果を定量化できないUpgradeには保守的な維持値を使い、価格だけで最優先にしない
- 最終復帰でも回収時間が最短の候補を選択
- 回収時間が同じ場合だけ価格をタイブレークに使用
- 診断理由を`最終復帰：施設回収時間`または`最終復帰：Upgrade回収時間`として表示

通常のBeam Searchは購入費を差し引いた600秒後の資産を比較しているため、安い施設が繰り返し選ばれること自体は状況によって合理的です。しかし診断理由が`最終緊急Fallback`だった場合、旧版は純粋な最安価格購入でした。v8.5ではこの経路もROI比較へ統一します。

v8.3からの修正は次のとおりです。

- 通常プランナーより前にROIフロンティア判定を実行
- 全施設のうち最短の回収時間と、全Upgradeの回収時間を直接比較
- Upgradeの回収時間が最良施設の105%以内なら、その場で購入または貯蓄を確定
- ROIフロンティアでは候補価格、`priority/critical`、Beam Utilityを使用しない
- 決定後は後段のBeam Search、価格Fallback、購入進行保証による上書きを禁止
- 判断表示へUpgrade回収時間と最良施設回収時間を併記

これにより、施設価格がUpgrade価格より安くても、施設の回収が200秒、Upgradeの回収が10秒ならUpgradeが確定します。価格の逆転を待つ経路はROIフロンティアを通過できません。

v8.2からの修正は次のとおりです。

- Upgrade目標候補から`upgradePriority/critical`必須条件を撤廃
- ストアに存在し、購入後増産量と回収時間を計算できる全Upgradeを投資集合へ登録
- 通常Upgrade、施設2倍Upgrade、クリックUpgrade、Kitten、Cookie Upgradeを同じ回収時間で比較
- 現在買える全候補の最良回収時間と各Upgradeの回収時間を直接比較
- Upgradeが最良投資なら、施設との価格大小に関係なく即時購入または直接貯蓄
- 分類フラグは戦略価値の補正にだけ使用し、候補参加条件には使用しない

この変更により、価格500のUpgradeを価格400の施設より先に買うかどうかは価格では決まりません。Upgradeの実効増産が50/秒、施設が2/秒なら、回収時間はそれぞれ10秒と200秒となり、Upgradeを選びます。逆に高価なUpgradeの回収が遅ければ施設を選びます。

v8.1からの修正は次のとおりです。

- クリックとCursorを同時に2倍にする最初の3Upgradeを独立したクリック基盤系列として扱う
- 表示名や翻訳ではなくUpgrade ID 0、1、2で識別
- Cursor 1個でID 0を取得後、そのままID 1を次の目標に設定
- ID 1の価格500へ届くまで固定待機上限を適用しない
- ID 1の待機中はCursorを含む施設購入を禁止
- Cursor 10個でID 2が解禁された後も同じ規則を適用
- パネルへID 0、1、2の未解禁・購入可能・購入済状態と実価格を表示

この3Upgradeは通常の施設2倍Upgradeではありません。クリック収益にも同じ倍率を与えるため、自動クリックを使用する戦略では基礎インフラに相当します。通常の施設ROIから推測させず、ゲーム固有の安定IDと解禁状態から戦略目標を決めます。

v8.0からの追加変更は次のとおりです。

- ページ共通の単一起動レジストリを追加
- 新版起動時に既存インスタンスのクリック・購入・戦略・UIタイマーを停止
- 全タイマーが実行権トークンを確認し、古いインスタンスは自己停止
- パネルへ`実行版`と`単一起動：有効`を表示
- 現在の所持金、実効収益、クリック収益、購入目標、全Upgrade候補評価を取得できる診断スナップショットを追加
- 購入結果が変わらない場合に、ロジックの誤判定と旧版による別購入を切り分け可能にした

v8.0以前には単一起動レジストリがないため、Tampermonkeyにそれ以前のスクリプトが複数登録されている場合だけは自動停止できません。導入時に旧版をすべて無効化または削除し、v8.1だけを有効にする必要があります。それ以後の版は新版から自動停止できます。

v7.15から購入中核を次のように再構築しました。

- 施設とUpgradeを共通の`取得時間＋回収時間`で順位付け
- 通常CpSと自動クリック収益を合算した実効収益をすべての候補評価に使用
- Upgrade購入後の実測CpS差、クリック収益差、内部メタデータ、説明効果のうち最も信頼できる増産量を採用
- 現在買える最良投資の回収時間と、未購入Upgradeの回収時間を直接比較
- 未購入Upgradeの回収が同等以上なら、価格までの固定ETA上限を適用せず投資目標化
- 既知のクリック2倍Upgradeは、カーソル施設だけでなく現在の自動クリック収益の増加を含めて評価
- 目標選択は候補種別別の優先度ではなく、取得時間と回収時間の合計を第一基準に統一
- 目標決定後は直接貯蓄と最大16件の先行購入経路を仮想比較
- 目標ETAを短縮する先行購入だけを許可し、購入後も目標を保持
- 購入失敗・状態反映遅延・例外時には別候補へ流れず、次周期に再評価

### 手根管予防クリーム

`Carpal tunnel prevention cream`はカーソル1個で解禁され、価格500、マウスとカーソルを2倍にします。自動クリックが毎秒20回なら、クリック単価2 Cookieの状態でクリック収益だけでも約40 Cookie/秒増えるため、回収時間は約12.5秒です。次のカーソルを繰り返し購入するより早く、カーソル1個と`Reinforced index finger`取得後から貯蓄対象になるのが基本動作です。クリック速度やBuffなどは固定値ではなく実ゲーム状態から再計算します。

v7.14からの主要な変更は次のとおりです。

- 固定300秒・1,800秒を中心にした施設2倍Upgradeの予約制限を撤廃
- 重要Upgradeを購入成功まで保持する目標コミットメントを導入
- 直接貯蓄した場合のETAを毎周期再計算
- 今買える最大16候補を1件ずつ仮想購入し、購入後の所持金・生産速度・Upgrade価格からETAを再計算
- 直接貯蓄より目標到達を0.25秒以上かつ0.1%以上早める購入だけを先行投資として許可
- 先行投資を行った後もUpgrade目標を解除せず、次周期に全経路を再比較
- 目標ETAを遅らせるグランマなどの反復購入を停止
- 予約Upgradeと許可された先行投資の購入失敗時は、別施設へフォールバックせず次周期に再試行

この方式では「待機上限を何秒にするか」は施設2倍Upgradeの中心判断ではありません。待機が長くても、全購入経路が目標到達を遅らせるなら直接貯蓄します。反対に、Cursorや別施設の購入が所持金減少を上回る増産を生み、目標ETAを短縮するなら、その購入だけを許可します。

v7.13からの主要な変更は次のとおりです。

- 施設2倍Upgradeの効果を`Upgrade価格 ÷ 対象施設数`でも評価
- 等価1施設価格が次施設価格の105%以内なら、CpS実測値に関係なく優位と判定
- 施設2倍Upgrade専用の予約到達上限を300秒から最大1,800秒へ拡張
- 優位判定後は対象施設を追加購入せず、Upgrade価格まで直接貯蓄
- Modやゲーム側のCpS状態反映順により回収時間が不安定な場合も価格関係で判定可能

`Steel-plated rolling pins`では、標準価格ならグランマ11個で`5,000 ÷ 11 ≒ 455`となり、次のグランマ価格約465を下回ります。この時点からグランマ購入を止めて5,000まで直接貯蓄します。グランマ28個では等価価格が約179、次のグランマ価格が約5,007なので、即座に予約対象とすべき状態です。

v7.12からの主要な変更は次のとおりです。

- 予約対象をIDと内部名で周期をまたいで保持
- 予約対象が購入可能になったら試行一覧をそのUpgrade 1件だけに限定
- 購入APIが失敗した場合も緊急施設Fallbackを禁止し、次周期に再試行
- 例外発生時も予約を保持し、例外復帰用の施設購入を禁止
- `bought`状態または施設数の変化で購入成功を確認した後だけ予約を解除
- 施設2倍Upgradeは評価期間内の純利益だけでなく、同じ施設を次に1個買う場合との回収時間で比較
- 施設2倍Upgradeの回収時間が次施設の105%以内になった時点から予約候補化
- `Child labor`は内部名でも工場2倍効果として認識し、日本語訳の有無に依存しない

`Child labor`は工場5個で解禁されますが、解禁直後に必ず買うのが最適とは限りません。標準価格・補正なしでは、工場5個時点の回収時間は約5,000秒で、次の工場1個は約1,006秒です。工場11個前後になると`Child labor`の回収時間が次の工場を下回るため、v7.13はこの時点を目安に予約します。割引、Buff、他Upgradeによって境界は動的に変わります。

v7.11からの主要な変更は次のとおりです。

- `desc`と日本語化された`ddesc`を合わせて解析
- `2倍`、`効率`、`マウス`、`クリック`、`カーソル`の日本語表現へ対応
- 序盤のクリック2倍Upgrade 3種を内部名で確定認識
- Cursorに紐付くUpgradeをクリック効果候補として評価
- 既知クリック2倍Upgradeは重要Upgradeに設定
- 通常の予約上限より長い最大300秒まで予約候補化
- 仮想実測が0かつ説明が日本語でも、現在クリック収益から2倍効果を復元

v7.11から引き継ぐ主要な変更は次のとおりです。

- `高価値Upgradeを予約購入`設定を初期ONで追加

- 予約判断をOpening Book直後、Beam Searchより前へ配置
- 予約待機を購入進行保証による強制施設購入の対象外に設定

- 画面の判断理由へ`Upgrade予約中`または`Upgrade予約購入`を表示

v7.10から引き継ぐ主要な変更は次のとおりです。

## 2 全体構造

```text
実ゲーム状態の取得
        ↓
Strategy State Machine
現在の目的と評価重みを決定
        ↓
候補生成
├─ 現在の施設
├─ 現在のUpgrade
├─ 未出現Upgradeの解禁連鎖
├─ 保証Fallback
└─ 購入対象またはコンボ開始条件を持つ待機
        ↓
Target ETA Chain ETA補正
        ↓
仮想状態を更新する2～3手Beam Search
        ↓
最良計画の先頭1手だけを実行
        ↓
実ゲーム状態を再取得して再計画
```

### 2.1 購入進行保証と適応型待機

購入判断は次の順番で確定します。

```text
現在の施設とUpgradeを列挙
        ↓
保証Fallbackを独立して列挙
        ↓
使用可能資金で買える候補数を確定
        ↓
1件以上
→ 原則BUY
→ 直接貯蓄ETAと先行購入後ETAを比較
→ 3秒以上かつ10%以上短縮できるか確認
→ 通常45秒、重要対象150秒以内だけWAIT
→ 上限後はBUYへ復帰

0件
→ 対象付き待機または貯蓄
```

`strictPurchaseProgress`がONの場合、適応型待機以外の処理が誤ってWAITを返しても、購入可能候補の先頭へ判断を差し替えます。候補なし判定や計画計算の例外が起きた場合も、Gameのストア情報から最安の購入可能品を直接取得して購入を試します。待機対象、開始時刻、周期数を保持し、購入成功時にリセットします。

この保証はクリック系コンボ実行中の短時間停止と、ユーザーが明示的にONにしたLucky銀行保護を除いて適用されます。

購入計画と購入実行は分離します。計画計算で2手目、3手目まで有望でも、複数購入をまとめて実行しません。ランダムイベント、価格変化、実績、Golden Cookie、研究完了などを取りこぼさないためです。

### 2.2 序盤Opening Book

Reinforced index fingerはCursorを1個所有すると解禁され、価格100でクリックとCursorを2倍にします。自動クリックを毎秒20回行う初期設定では、Cursorを追加購入して受動CpSを少し増やすより、クリック収益を2倍にするUpgradeへ直行する方が有利です。

```text
Cursor 0個
→ 15 CookieでCursorを1個購入

Cursor 1個、Reinforced index finger未購入
→ 追加Cursorを買わない
→ 100 Cookieまで待つ
→ Reinforced index fingerを購入

取得後
→ 通常の複数期間評価とBeam Searchへ移行
```

この規則は`openingBookEnabled`、`autoClick`、施設購入、Upgrade購入がすべてONの場合だけ適用します。手動中心のプレイでは無効化でき、通常評価へ戻せます。Upgradeのストア表示更新が遅れた場合も、ゲーム内Upgradeオブジェクトを参照して待機対象を保持します。

## 3 Strategy State Machine

| 状態 | 目的 | 購入と待機の方針 |
|---|---|---|
| `BOOTSTRAP` | 基礎生産と初期施設を作る | Productionを強く評価し、買える候補を積極的に購入 |
| `UNLOCK` | Lucky day、Serendipity、Get lucky、Grimoire等を解禁 | Unlock連鎖を強く評価 |
| `BUILD` | 次の解禁とコンボ能力を作る | Production、Unlock、Comboを均衡評価 |
| `COMBO_PREP` | Magicと銀行残高を準備 | ComboとLiquidityを優先し、少額の戦略保護額を設定 |
| `COMBO_WAIT` | Magicを保持しNatural GCを待つ | 不要な購入を抑え、待機アクションを優先可能にする |
| `COMBO_EXECUTE` | Natural buffとFtHoFを重ね、クリック収益を得る | Click Frenzy等の実行中は購入を停止してクリックを優先 |
| `WINDFALL_SPEND` | コンボ等の大収益を再投資 | ProductionとUnlockを強く評価し、資金拘束を弱める |
| `SEASON_RESEARCH` | 季節UpgradeまたはResearchを進める | 通常ROIで測りにくい恒久進行をUnlock価値として評価 |
| `ASCEND_READY` | Ascend可能な段階を知らせる | 自動Ascendはせず、Advisor表示と資金保全を行う |

状態判定は原則として上から優先されます。Click Frenzy等の実行状態、大収益直後、Ascend推奨、序盤、主要機能未解禁、季節・研究、コンボ条件、通常構築の順で判定します。

### 3.1 状態遷移の主条件

- `COMBO_EXECUTE`: Click Frenzy、Dragonflight、Elder Frenzyが有効、またはMagicが足りてNatural buffが有効
- `WINDFALL_SPEND`: 直前の所持Cookie増加が基礎CpSの600秒分以上で、検出後30秒以内
- `ASCEND_READY`: Ascend Advisorがstrong判定
- `BOOTSTRAP`: 周回総生産が100万未満、または総施設数が15未満
- `UNLOCK`: Golden Cookie基本3種が未取得、またはGrimoireが利用不能
- `SEASON_RESEARCH`: 進行中Researchまたは現季節の未取得Upgradeが存在
- `COMBO_WAIT`: Grimoireが利用可能でFtHoF分のMagicが満タン
- `COMBO_PREP`: Grimoireは利用可能だがMagic不足
- `BUILD`: 上記以外

状態は固定されません。毎秒再判定し、現在のゲーム状態へ追随します。

## 4 購入候補

### 4.1 現在候補

現在購入できる、または価格が見えている施設とUpgradeを列挙します。施設とUpgradeは同じ候補集合で比較します。

通常候補の基本評価はv6.0と同じです。

```text
基本Score = 購入可能になるまでの時間 + 価格 / 経済収益増加量
```

経済収益には通常CpS、自動クリック、Wrinklerの長期効果を含めます。現在の購入資金として使える速度と、長期経済速度は分離します。

### 4.2 Upgrade優先評価

Upgradeは施設より効果の再現が難しく、`bought=1`だけの仮想評価では差分が0になる場合があります。v7.12は次の3経路を独立して計算し、最も妥当な効果量を採用します。

1. 仮想購入後に`CalculateGains()`を実行した実測差分
2. Golden Cookie、Research、割引など既知の戦略価値
3. Upgradeメタデータと現在経済から求める効果量推定

| Upgrade種別 | v7.12の効果量推定 |
|---|---|
| 施設2倍・Tier | 対象施設の現在総生産 × `(倍率 - 1)` |
| Mouse、Finger、Click倍率 | 現在の1クリック収益 × 自動クリック回数 × `(倍率 - 1)` |
| クリック固定加算 | 1クリック加算値 × 自動クリック回数 |
| Cookie全体倍率 | 現在の受動生産 × 表示百分率 |
| Cookie pool | 現在の受動生産 × `power / 100` |
| Synergy | 対象2施設の現在生産と倍率から推定 |
| Kitten | 実測値を優先し、取得できない場合はMilkと現在経済から推定 |
| Golden Cookie系 | Golden Cookie期待収益を追加 |
| 施設・Upgrade価格割引 | 再投資資金の購買力上昇を等価収益へ換算 |
| Research | 生産差分に加えて解禁連鎖価値を追加 |
| 未定量Utility | 現在経済収益の0.2%を与えて候補を維持 |

1クリック収益は実ゲームの計算を反映する`Game.mouseCps()`を優先し、利用できない場合だけ`computedMouseCps`を参照します。これに設定された自動クリック回数を掛けた値を、購入に使える収益として扱います。説明文から`twice as efficient`、倍率、百分率、1クリック固定加算を抽出し、`buildingTie`、`buildingTie1/2`、`power`、`pool`と組み合わせます。

実測値が得られた候補の確信度は100%とします。メタデータ推定では認識できた情報に応じて確信度を設定し、UIへ評価モデルとともに表示します。一度購入すれば価格上昇なしで永久に効く性質を0.90倍のScore補正として反映します。戦略UpgradeのScoreは0.60倍、その他のUpgradeは0.72倍とし、最良Upgradeの補正後Scoreが最良候補の120%以内なら施設よりUpgradeを選びます。

Beam Searchでは上位候補が施設だけで埋まらないよう、1ノード8候補のうち3枠をUpgrade用に確保します。解禁連鎖にも2枠を確保し、残りを総合順位で埋めます。

### 4.3 解禁連鎖候補

未出現Upgradeは価格だけで評価できないため、解禁までに必要な次の1個を候補化します。

- 施設Tier Upgrade: 次の施設数閾値までの施設購入
- Synergy Upgrade: 対応する2施設の不足数
- 建物実績: 次の実績閾値とMilk増加
- Kitten: 次の実績取得でKitten条件を満たす場合の連鎖
- Research: Elder実績、Grandma type、Grandma数を進める施設購入
- Golden Cookie基本3種: クリック数進捗を監視
- Mouse Upgrade: 手焼きCookie進捗を監視
- Fortune、Season: ランダムまたは固有条件を監視

Beam Searchでは通常の施設候補と、その施設が解禁連鎖の次の一手である候補を別経路として保持します。施設購入後は仮想施設数を更新し、Tier Upgrade、建物実績、Kitten、Synergyの条件を再判定します。条件を満たしたUpgradeは次の探索ノードで候補として出現します。仮想状態は探索終了時に完全に復元します。

### 4.4 Fallback候補

通常シミュレーションが失敗しても自動購入を止めないため、次の独立した経路を維持します。

1. 通常候補
2. Gameオブジェクトから直接作る保証Fallback
3. 同周期で別の購入可能候補を最大8件試行
4. ROIを使わず最安品を直接試す最終緊急Fallback

同一の実物が通常候補とFallbackに現れた場合は、通常評価を優先して重複除去します。

## 5 Target ETA

Target ETAは、今買える候補Aが、すでにストアへ出ている高価なUpgrade Bへの到達を早めるかを測ります。

```text
Direct ETA(B)
= max(B価格 - 現在資金, 0) / 現在の計画収益速度

Via A ETA(B)
= max(A購入後のB価格 - A購入後資金, 0) / A購入後の計画収益速度

ETA短縮
= Direct ETA - Via A ETA
```

Aの購入費で所持金が減るため、CpSが増えるだけでは加点されません。支出を含めてもBへ早く届く場合だけ正の短縮となります。

価格割引Upgrade Aでは、仮想購入後にBの価格を再取得します。Golden Cookie強化Upgrade Aでは、仮想購入後のGC期待収益を計画収益速度へ反映します。仮想評価中は`Game.Win`と`Game.Unlock`を一時的に無効化し、現実のセーブへ実績やUnlockを発生させません。評価後は`finally`で状態と`CalculateGains()`を復元します。

Target ETAは候補を強制購入する機能ではありません。候補の基本Scoreを最大80%の範囲で改善し、Beam Searchへ渡す候補順を補正します。

### 5.1 複数期間の将来資産評価

単発の回収時間だけでは、長く効くUpgradeと短期の施設購入を正しく比較できません。各候補について、何も買わない場合と候補を買う場合の資産を1分、5分、15分後に比較します。

```text
直接資産(H)
= 現在資金 + 現在収益速度 × H

購入後資産(H)
= 購入時の残高
  + (現在収益速度 + 生産差分 + コンボ期待収益率) × 購入後の残り時間

複数期間価値
= 1分差 × 50% + 5分差 × 35% + 15分差 × 15%
```

資産差を現在収益速度で割って「時間相当価値」に直し、基本Scoreに対する相対比へ変換します。正の価値はScoreを除算し、負の価値はScoreを乗算します。補正倍率は最大4に制限します。v7.4までの単純減算は強い候補をすべて最小値へ潰す可能性がありましたが、相対倍率方式では候補間の順位差を維持できます。購入可能になるまでに評価期間を超える候補は、その期間の加点を受けません。

### 5.2 Chain ETA

Chain ETAは、まだストアへ出ていないUpgradeを解禁して購入するまでの到達時間を扱います。

```text
Direct Chain ETA
= max(解禁に必要な施設費 + Upgrade価格 - 現在資金, 0)
  / 現在の計画収益速度

Via A Chain ETA
= max(A購入後の残り解禁費用 - A購入後資金, 0)
  / A購入後の計画収益速度
```

候補Aが解禁条件を直接進める場合は、解禁連鎖の残り費用からAの購入分を減らします。候補Aが生産力や価格を改善する場合も、購入後の計画収益速度で再計算します。Target ETAとChain ETAの両方が有効な場合は、短縮率の大きい方を候補の補正理由として表示します。

## 6 コンボ期待価値

通常時のCpS差分だけでは、クリック系Upgrade、Golden Cookie強化、Kitten、Dragon関連、Godzamok準備施設を過小評価します。v7.12は受動CpSと自動クリック生産を基礎経済へ入れ、候補ごとにコンボ期待収益率を推定して探索期間内の価値へ換算します。

```text
コンボ価値
= コンボ期待収益率 × 探索期間の残り時間 × 状態別Combo重み
```

評価対象は次のとおりです。

- Mouse、Finger、Click、Kitten系: クリック収益の増加を追加評価
- Lucky day、Serendipity、Get lucky、Golden Cookie系: GC頻度、効果時間、成立率を追加評価
- Dragon、Godzamok関連: コンボ能力として追加評価
- Farm、Mine、Factory、Shipment等: Godzamok売却燃料として少量の準備価値を付与

この値は期待値であり、FtHoF結果やGolden Cookieのランダム性を確定予測するものではありません。

## 7 Beam Search型購入プランナー

初期値は深さ3、幅8、各ノードの購入候補上限8です。設定値により深さは2または3へ制限します。

### 7.1 探索ノード

各ノードはアクション列と評価値を持ちます。そのアクション列を実ゲームの一時コピーへ適用し、次の情報を毎回再取得します。

- 仮想銀行残高
- 実際のGame価格関数で再計算した価格
- `CalculateGains()`後の計画収益速度
- 仮想施設数と購入済みUpgrade
- 仮想実績数とMilk
- 新たに出現したUpgrade
- 経過時間
- これまでのアクション列
- 累積Unlock価値
- 累積コンボ期待収益率
- 評価Utility

仮想状態の作成時は、所持Cookie、全施設の`amount`と`bought`、全Upgradeの`bought`と`unlocked`、実績の`won`、実績数、Milkを保存します。アクション列を適用した後に`CalculateGains()`を実行し、候補を再生成します。探索終了時は保存した値を復元します。施設価格は固定15%近似ではなく、その仮想状態でゲームの価格関数を呼び直します。

### 7.2 待機アクション

待機アクションは対象と終了条件を持ちます。購入対象の場合は、現在資金と計画収益速度から購入可能になるまでの時間を計算し、最大150秒以内なら候補化します。

```text
waitTarget = 購入対象
waitUntil = affordable
waitDuration = min(購入可能になるまでの時間, 最大待機時間)
```

となり、次の深さで高価な候補を購入できる可能性が生まれます。これにより、次のような列を直接比較できます。

```text
Farm 25個到達
→ Double farmまで5秒待機
→ Double farm購入

Kitten workersまで34秒待機
→ Kitten workers購入
→ 次の状態から候補を再生成
```

コンボ待機は購入対象ではなく、Natural Golden Cookieまたは待機上限を終了条件にします。実際の実行では待機を一括消化せず、次の購入周期で条件を再確認します。そのため、対象が早く購入可能になった場合やGolden Cookieが出現した場合は直ちに再計画できます。

実ゲームへ適用する待機は、購入可能候補が0件の場合を除き、次の条件をすべて満たす必要があります。

```text
Direct ETA
= max(目標価格 - 現在資金, 0) / 現在収益

Via Purchase ETA
= max(仮想購入後の目標価格 - 仮想購入後資金, 0)
  / 仮想購入後収益

短縮秒数 = Via Purchase ETA - Direct ETA
短縮率 = 短縮秒数 / Via Purchase ETA
```

- 対象がUpgrade、重要候補、または解禁先Upgradeを持つ候補
- `Direct ETA`が通常候補では45秒以内
- Kitten、Golden Cookie、Research、解禁連鎖などでは150秒以内
- 短縮秒数が3秒以上
- 短縮率が10%以上
- 非重要対象は補正後Scoreが最良即時購入候補の1.25倍以内
- 経過実時間と最大周期数の両方が上限未満

購入周期が1.5秒なら、通常候補は最大30周期、重要候補は最大100周期です。毎周期、価格、資金、収益、候補を再取得します。対象が途中で変わっても待機開始時刻と周期数は引き継ぐため、候補を切り替えて上限を回避できません。購入成功時にガードをリセットします。

候補の重複判定には品目だけでなく、通常購入、解禁連鎖、将来目標などの計画上の役割も含めます。同じUpgradeや施設を指す場合でも、解禁経路としての情報を消さずにBeam Searchへ渡します。

### 7.3 Utility

探索ノードの比較値は次の要素で構成します。

```text
Utility
= 将来銀行残高
 + 将来収益速度 × 残り探索時間
 + Unlock価値
 + コンボ期待価値
 - 戦略保護額不足ペナルティ
 - 待機遅延ペナルティ
```

各項目には現在のStrategy Stateに応じた重みを掛けます。たとえば`UNLOCK`ではUnlockを強くし、`COMBO_WAIT`ではComboとLiquidityを強くします。

### 7.4 実行規則

最良ノードのアクション列から先頭だけを実行します。

- 先頭が購入: 対象を1個購入
- 先頭が待機: 購入可能品が0件、または適応型待機条件を満たす場合だけ今周期は購入せず再計画
- 購入失敗: 同周期の別候補、Fallback、緊急Fallbackへ進む

計画列を一括実行しないため、実ゲームと仮想状態のずれが累積しません。

## 8 戦略保護額

手動Lucky銀行をONにした場合は、従来どおり保護額を設定します。戦略状態による自動保護額は購入停止の原因になったため、v7.12でも初期OFFです。ユーザーが明示的にONにした場合だけ次の自動保護額を使用します。

| 条件 | 保護額 |
|---|---:|
| 手動Lucky銀行ON、基本3種取得済み | 基礎CpSの42000秒分 |
| 手動Lucky銀行ON、基本3種未完了 | 基礎CpSの6000秒分 |
| `COMBO_WAIT`、基本3種取得済み | 基礎CpSの6000秒分 |
| `COMBO_WAIT`、基本3種未完了 | 基礎CpSの1200秒分 |
| `COMBO_PREP` | 基礎CpSの300秒分 |
| `ASCEND_READY` | 基礎CpSの600秒分 |
| その他 | 0 |

購入候補の価格判定には、所持Cookieから保護額を引いた使用可能Cookieを使います。

## 9 コンボ実行

GrimoireはMagicが足りるだけでは詠唱しません。Frenzy、Dragon Harvest、Building Special等のNatural buffを確認してからFtHoFを使います。

```text
Magic不足
→ COMBO_PREP

Magic満タンでNatural buffなし
→ COMBO_WAIT

Natural buff発生
→ COMBO_EXECUTE
→ FtHoF
→ Golden Cookie自動クリック

Click Frenzy Dragonflight Elder Frenzy中
→ 購入を一時停止
→ 大クッキークリックを優先
```

通常Frenzyだけで購入を一律停止する設定にはしていません。クリック系の高倍率コンボ中だけ自動的に購入を止めます。従来の「高倍率Buff中は購入停止」設定は手動オプションとして残します。

## 10 UIと診断

ステータスには次の情報を表示します。

- 現在のStrategy State
- 現在の戦略目的
- 表示CpS、現金化速度、長期経済速度、所持Cookie
- 戦略保護額と使用可能Cookie
- 現在の購入、魔法、Wrinkler処理
- 通常候補、購入可能候補、Fallback候補、解禁候補の件数
- 所持金では購入可能だが保護額で遮断された候補数
- 連続未購入周期と最終購入時刻
- Target ETAとChain ETAの目標数、候補A、目標B、Direct ETA、Via A ETA、短縮時間
- Beam Searchの深さ、展開ノード数、計画列
- 待機対象、終了条件、最大待機時間
- 適応型待機のETA短縮秒数、短縮率、現在周期数と上限
- 選択候補の複数期間資産効果

- 上位購入候補

## 12 安全性と回帰防止

- 仮想評価で実際の`buy()`を呼ばない
- 仮想評価後はCookie、施設数、Upgrade状態、実績状態、`Game.Win`、`Game.Unlock`を復元
- Target ETA、Chain ETAまたはBeam Searchが失敗しても通常候補を削除しない
- Beam Searchが計画を返さなくてもv6.0のimmediate-first判断へ戻る
- 購入可能候補がある場合、適応型待機以外のWAITを無効化してBUYを維持する
- 適応型待機はDirect ETA、Via Purchase ETA、時間、周期数をすべて制限する
- 全ストアUpgradeを候補へ残し、Beam SearchにUpgrade専用枠を確保する
- 候補なし判定または計画例外時にも緊急Fallbackを試す
- 探索が120ミリ秒へ達した場合は打ち切り、それまでに得られた最良計画を使用する
- 購入API失敗時は同じ周期で別候補を試す
- 最後にGameストアを直接確認する緊急Fallbackを使う
- `Chocolate egg`は自動購入しない
- prestige、debug、toggle poolを通常購入対象から除外
- Ascendは助言表示のみで、自動実行しない

## 13 検証

完成版TXTに対してJavaScript構文検査を行います。さらに独立した模擬ゲーム状態で次のケースを確認します。

1. `computedMouseCps`が0でも`Game.mouseCps()`から1クリック生産を取得できること
2. 自動クリック生産が1クリック生産×設定クリック回数になること
3. クリック2倍Upgradeを現在クリック収益と自動クリック回数から評価できること
4. クリックUpgradeが通常施設より有利な状態で、購入判断と実購入の両方がUpgradeを選ぶこと
5. Golden Cookie期待値へクリック生産が含まれること
6. Target ETAが受動CpSと自動クリック生産の合計で計算されること
7. 非重要かつ低価値な将来対象を待機対象にしないこと
8. 同じ品目の通常候補と解禁候補が役割別に保持されること
9. 実画面由来のCursor 18、Upgrade 500、自動クリック20回/秒で、0.418秒の小さな遅延でもUpgrade貯蓄を選ぶこと
10. Grandma 6個、次Grandma 232、2倍Upgrade 1,000で、約0.2秒の遅延でもUpgrade貯蓄を選ぶこと
11. 同じ状態で判断理由が`Upgrade予約中`となり、施設購入へフォールバックしないこと
12. 1,000 Cookie到達時に予約したGrandma Upgradeを購入対象にすること
13. 日本語説明だけで仮想実測が0でも、Carpal tunnel prevention creamをクリック2倍として評価すること
14. Cursor 18を買わず、500 CookieのクリックUpgradeを`Upgrade予約中`にすること
15. 予約Upgradeの価格へ到達した周期の購入試行一覧が対象Upgrade 1件だけになること
16. 予約Upgradeの購入APIが一時失敗しても、同じ周期に施設を購入せず予約を保持すること
17. 予約購入中に例外が発生しても緊急Fallbackで施設を購入しないこと
18. 標準条件のFactory 5個では`Child labor`をまだ予約せず、Factory 11個前後では次Factoryより回収が速いため予約候補にすること
19. スクリプト全体がJavaScript構文検査を通過すること
20. グランマ10個では金属製めん棒より次グランマが優位、11個では金属製めん棒が優位へ切り替わること
21. 金属製めん棒を目標にした状態で、次グランマ購入後のETAが直接貯蓄より長ければ購入を拒否すること
22. 別施設の先行購入が金属製めん棒へのETAを短縮する場合は、その1件だけを許可して目標を保持すること
23. 先行購入後の周期で全候補を再計算し、過去の計画を盲目的に連続実行しないこと
15. JavaScript構文検査を通過すること

ブラウザ実機では、Cookie Clickerの現在セーブやMod構成によってGameオブジェクトの内容が変わるため、UIの購入診断と「今すぐ買えるものを1つテスト購入」も併用します。

## 14 導入手順

1. Tampermonkeyで旧版のコードを開く
2. 旧コードをすべて削除する

4. Cookie Clickerを再読み込みする
5. パネルに`v8.5`と表示されることを確認する
6. Upgrade効果量詳細評価、序盤の定石、Strategy State Machine、Beam Search、Target ETA、Chain ETA、複数期間評価、適応型待機がONであることを確認する

## 15 制約

- Beam Searchは主要な購入関連状態をコピーしますが、Cookie Clickerの全内部状態を完全複製するものではありません
- Tier Upgrade、建物実績、Kitten、Synergyの主要条件は仮想状態内で更新しますが、ランダムドロップや時間依存Researchの完了までは仮想発生させません
- 未出現Upgradeの全条件を一般式で再現せず、主要な施設Tier、Synergy、実績、Kitten、Researchを扱います
- Golden Cookieとコンボの価値は期待値であり、次の結果を予知しません
- Garden、Pantheon、Dragon Aura、Stock Market Loan、dualcastの完全自動操作は本版の対象外です
- `buyFunction`だけで特殊効果を実装するUpgradeは、`bought=1`の仮想評価で完全再現できない場合があります
- Upgradeの最低戦略価値は、効果を仮想状態で再現できない場合の保守的推定です
- 理論上の完全最適化ではなく、購入停止を防ぎながら短期と中長期の効率を安定して改善する設計です
